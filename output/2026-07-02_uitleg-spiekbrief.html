VitaCall — spiekbrief voor het mondeling

Niet inleveren. Dit is jouw voorbereidingsdocument: per sectie wat er staat, waarom die keuze, en de vragen die de docent waarschijnlijk stelt. De NVD kwam door de toelichtingseis — dit document bestaat om dat gat te dichten.

Het verhaal in één minuut. VitaCall is een alarmcentrale. Spraak wordt op de edge (Raspberry Pi) omgezet naar tekst zodat audio het pand nooit verlaat; alleen tekst gaat naar de cloud (Render), waar een classifier de urgentie inschat. Twee modellen, twee deployments, één pipeline eromheen met validatie, CI/CD met een echte deploy-gate, en monitoring met drift-detectie en alerts. Alles wat het notebook claimt is live na te klikken of staat als uitgevoerde cel-output erin.

Sectie 0-1 — Datapipeline (LD1 + LD2)

WatDrie lagen: ruw → schoon → trainklaar, gebouwd rond de DataPipeline-klasse met per laag een validatiestap (dataclass-checks, fail-fast ValueError). SHA256-manifest pint de artefacten vast.
WaaromDocentfeedback eerste kans: te veel herhalende code, meer OOP. De klasse bundelt ingest/clean/split; elke laag is los aanroepbaar en testbaar.
SchaalStreaming met pyarrow.iter_batches (constant geheugen), PySpark voor de distributed split (verplicht, geen stille pandas-fallback), 250k-rijen-stresstest, fsspec zodat lokaal pad en S3-pad dezelfde code gebruiken.
Waarom Spark als het toch op één laptop draait? — Spark local mode gebruikt dezelfde API en hetzelfde executieplan als een cluster; de partition-scaling-meting (1.5.1) laat zien dat de speedup met partities meegroeit. Op een echt cluster verandert alleen de master-URL.
Wat gebeurt er als er kapotte data binnenkomt? — De validatielaag gooit een ValueError met de reden; de pipeline stopt liever hard dan dat er stil vervuilde data doorstroomt (fail-fast).

Sectie 2.1 — Edge-ASR: Whisper-tiny finetune (LD3)

WatWhisper-tiny gefinetuned op 360 synthetische zorg-clips (gTTS uit domein-templates) + 300 clips Multilingual LibriSpeech NL. Encoder bevroren (2GB VRAM), fp16, checkpoints, tijdsbudget-probe. Held-out testset: 20 zorg-zinnen die nooit getraind worden.
Waarom niet VoskEerste inlevering gebruikte Vosk-NL: een voorgetraind Kaldi-model dat je niet kunt bijtrainen. Precies het feedbackpunt. Whisper is een PyTorch-model, dus finetunen kan wel.
Eerlijk resultaatWER 0.293 → 0.330: de lichte finetune verbetert de zorg-testset niet. Analyse in het notebook: 100 stappen binnen het 35-minutenbudget is te weinig (de loss daalde nog toen de learning-rate al was afgebouwd) en de transcripties schuiven qua stijl op naar de MLS-audioboeken. We rapporteren beide metingen en benoemen wat een langere, zorg-zwaardere run zou moeten veranderen.
Je WER werd slechter — waarom lever je dat in? — Omdat het gemeten is. Een negatief resultaat wegmoffelen of alleen het beste getal tonen is precies wat MLOps-monitoring moet voorkomen. De meting, de analyse en het verbeterplan staan er; dat is hoe een experiment hoort te werken.
Waarom synthetische zorgdata? — Echte alarmcentrale-audio is AVG art. 9-gezondheidsdata; die mag ik niet gebruiken. gTTS-zinnen uit domein-templates + openbare NL-spraak (MLS) is de wettige route. De testset is ook synthetisch en dat benoem ik als beperking.
Debugverhaal (goud voor "leg je code uit"): de eerste finetune-runs hadden een loss van 28 waar ~1.8 hoort. Per-token-analyse liet zien dat positie twee vrijwel alle loss droeg: de labels bevatten al een <|startoftranscript|>-token terwijl Whisper er bij het verschuiven zelf één toevoegt. Het model trainde op een verschoven reeks met dubbele starttoken. Fix: starttoken uit de labels strippen; een test bewaakt dat de forward-loss van het voorgetrainde model onder de 3 blijft.

Sectie 2.2-2.9 — Cloud-model (LD3)

WatTF-IDF + Logistic Regression op DBRD (boekreviews als proxy), domein-zinnen ge-oversampled. Dummy-baseline → heavy → grid-sweep → multi-model-vergelijking → Optuna; winnaar gepromoveerd naar models/sentiment_heavy.pkl. Alles in MLflow (40+ runs).
EvalAccuracy + gewogen F1, 5-fold StratifiedKFold met shuffle (duplicaat-seeds zouden anders in één fold clusteren), confusion matrix, ROC, calibratie. Test-set wordt één keer gebruikt: finale go/no-go bij promotie.
ExtraLite-variant (JSON, 12.7× kleiner) als offline fallback; FedAvg-experiment met gedeelde vectorizer en warm-start clients — privacy vs. accuracy zichtbaar gemaakt.
Waarom boekreviews voor een alarmcentrale? — Grootste openbare NL-sentimentset; echte transcripten mogen niet (AVG). Domein-oversampling leert het model spoed-vocabulaire; de coëfficiënten-cel laat zien dat "geen pijn" als bigram het rustig-signaal draagt.
Wat doet Optuna anders dan grid search? — Bayesiaans zoeken: elke trial gebruikt de uitkomsten van eerdere trials om kansrijker hyperparameters te kiezen; grid probeert alles blind. Zelfde zoekruimte, minder trials nodig.

Sectie 3 — Deployment (LD4)

CloudDocker-image (non-root, gepinde deps, healthcheck) live op Render: https://mleops.onrender.com. Bewijscel vergelijkt de deployed commit (RENDER_GIT_COMMIT in /health) met de lokale git-HEAD: onweerlegbaar dat de live service déze code draait.
CD-gaterender.yaml heeft autoDeployTrigger: checksPass: Render deployt pas nadat de GitHub Actions-checks groen zijn. Rode CI = geen deploy.
EdgeHet gefinetunede model geconverteerd naar ggml, op de Pi gequantiseerd naar q5_0 (28MB), draait als systemd-service (vitacall-asr, poort 8080, MemoryMax). Bewijscel: ssh leest /proc/device-tree/model ("Raspberry Pi Zero 2 W") + live transcriptie via HTTP. Keten-cel: wav → Pi-transcript → Render /analyze.
CI/CD/CTEén workflow (cicd.yml): smoke-test → docker-build met harde health-assert → wekelijkse hertraining via nbconvert (CT), artifacts geüpload.
Waarom geen Docker op de Pi? — 512MB RAM waarvan Pi-hole al ~200MB gebruikt; de Docker-daemon kost 100-150MB. Bare-metal whisper.cpp + systemd geeft dezelfde herstart-garanties zonder die overhead. Containerisatie toon ik aan via de Render-image en de CI docker-build.
Is dit niet deels handmatig? — De cloud-keten is volledig automatisch (push → CI → gate → deploy). De edge-deploy is een gescript proces (deploy_pi.sh: build, model, service, smoke) — herhaalbaar met één commando per stap.

Sectie 4 — Monitoring (LD5)

Systeemp50/p95-latency, error-rate, request-tellers; live gescrapet van de Render-/metrics en als Prometheus-exposition geëxporteerd.
ModelDriftDetector op de input-verdeling (PSI + KS-test), output-drift, kwaliteits-drift met bekende-uitkomst-scenario's (spoed-recall).
ActieAlert-engine met regels + drempels (drift > 0.30, PSI > 0.20 → retrain_recommended), dashboard-cel, en de koppeling naar CT: de wekelijkse retrain is de opvolging van zo'n alert.
Hoe weet je dat je alerts werken? — Twee kanten getest: gesimuleerde drift-scenario's waarvan de uitkomst vooraf vaststaat (moeten afgaan) én de echte live tellers in gezonde toestand (moeten 0 alerts geven). Beide staan als celoutput in het notebook.

Zwaktes die je zelf moet benoemen (voordat de docent het doet)

  • Zorg-testset is gTTS-audio: veld-WER ligt hoger. Mitigatie: MLS-holdout als tweede, niet-synthetische meting.
  • Finetune-winst bleef uit (0.293 → 0.330); analyse + verbeterplan staan in 2.1. Zeg dit zelf, vóór ze het vragen.
  • Spark draait local mode; echt cluster is de logische vervolgstap, de code is er klaar voor.
  • FedAvg is een simulatie zonder netwerk-transport; het algoritme is volledig, transport is infra.
